----------------------------------------------------------------------
1. THE IDEA
----------------------------------------------------------------------
BidMagnet (formerly Tender Copilot) helps Spanish IT companies (20-500 staff)
win public contracts. These companies find tenders late, can't judge whether
a tender is worth it, lose bids over a missing document, and guess at prices.
The product finds relevant tenders, scores them, and prepares the bid
groundwork: a checklist with page citations, a price simulation and a
proposal draft.

Jyothika's part: the data (Miguel: "data scraping and cleaning" by Saturday).

Agreed stack: Supabase (database + file storage + email login), Python
scripts for data, Next.js on Vercel for the website.
Demo strategy: real data, a few tenders prepared in depth ahead of time,
nothing that can fail live.

4. STEP BY STEP
----------------------------------------------------------------------

(1) FETCHING – placsp_fetch.py
  PLACSP publishes tenders as Atom feeds: a standard "list of updates"
  format, like a news feed, where each item is a block of XML (CODICE).

  Mode         Command               What you get                                 Use
  monthly zip  month 202609          every tender touched that month              history (buyers, winners, prices)
                                     (193 files, 2.9 GB XML unzipped)
  live feed    live --pages 3        newest ~500 updates per page, newest first;  daily updates
                                     each page links to the next older one
  documents    docs --open-only      PCAP + PPT PDFs for tenders still open       checklist extraction

  Problems handled:
  - Certificate: PLACSP's HTTPS certificate is issued by FNMT (Spanish
    government CA), which Mac/Linux don't trust by default. We load
    certs/fnmt_chain.pem explicitly instead of switching security off.
  - Slow, flaky server (~100 KB/s, dropped connections, no resume):
    3 retries; downloads go to a .part file first so a half file never
    looks complete.

(2) PARSING – placsp_parse.py
  - Streams the XML one tender at a time, so 2.9 GB never needs to fit in
    memory. A full month takes about 2 minutes.
  - Per tender it extracts:
      basics        id, title, status, link, last-updated time
      buyer         name, tax ID (NIF), city, place in government hierarchy
      money         budget excl./incl. VAT, estimated total value
      what          CPV codes, contract type, procedure, duration, lots
      when          bid deadline date and time
      criteria      each award criterion + weight (e.g. "Price, 70")
      requirements  solvency (turnover, experience), declarations, classification
      documents     links to PCAP, PPT, annexes, award notices
      results       winner + NIF, bids received, lowest/highest bid,
                    award amount, date
  - IT filter on CPV codes: 72* (IT services) and 48* (software) = core;
    302* = hardware; 3242*/6421* = telecom/network.
  - Duplicates: a tender reappears at every status change
    (PUB open -> EV evaluating -> ADJ awarded -> RES resolved).
    latest_versions() keeps only the newest version. It also handles
    deletion markers ("tombstones") for withdrawn tenders.

(3) BUILDING – build_dataset.py
  Keeps only IT tenders and writes to out/:
    tenders.jsonl   full nested record per tender (29 MB); this is what
                    gets loaded into Supabase
    *.csv           tenders, criteria, documents, results, requirements
                    (open in Excel)
    stats.md        coverage numbers
  Also works out: region (from the EU NUTS location code), price weight,
  and whether the PCAP/PPT PDFs exist.

(4) STORING – load_supabase.py -> Supabase
  Table                 One row =                 Used for
  tenders               one tender                feed, search, filters, deadline board
  tender_criteria       one award criterion       "Price 70%, training 10%"
  tender_documents      one PDF link              download links
  tender_results        one award (per lot)       buyer profile: winners, discounts, bid counts
  tender_requirements   one requirement           eligibility check
  tender_extractions    one cited checklist       checklist screen

  Rules:
  - Newer wins: a tender is only overwritten if the incoming version is
    newer, so re-runs and out-of-order loads are safe.
  - Batches of 200, saved as it goes: a full month loads in 16 seconds,
    and an interruption doesn't lose everything.
  - Security: logged-in users can read; only the pipeline (with the DB
    password) can write.
  - Space: 52 MB of 500 MB free, so room for about 8-9 more months.

(5) PDFs
  - Supabase stores only the links (38,049 of them).
  - Downloaded so far: 4 PDFs for 2 open tenders, on the laptop in
    raw/docs/. NOT in Supabase Storage yet.

(6) CITED CHECKLIST – extract_tender.py
  - Input: a tender's PDFs. Output: out/extractions/<id>.json with:
      summary, key dates, envelopes, mandatory documents, eligibility,
      award criteria, price formula, abnormally-low-bid rule,
      exclusion risks, contradictions.
  - Every item carries doc + page + quote.
  - Verification: the script opens the PDF and checks that the quote
    really appears on that page (verified: true/false).
  - Two ways to run it:
      With Claude API: automatic; needs a paid key (~$0.50-1 per tender).
      Free:            Claude Code writes the JSON in chat, then run
                       `uv run --with pymupdf extract_tender.py <id> --verify`.

(7) USING IT (not built yet)
  The Next.js app reads Supabase with the Project URL + anon key:
  feed of open IT tenders, tender page, buyer profile (tender_results),
  checklist (tender_extractions).

----------------------------------------------------------------------
5. HOW "REAL-TIME" WILL WORK (daily job)
----------------------------------------------------------------------
  Every day 05:30 UTC, GitHub Actions (.github/workflows/daily-ingest.yml):
    1. placsp_fetch.py live --pages 3     (~1,500 newest updates)
    2. build_dataset.py raw/live          (parse + IT filter)
    3. load_supabase.py                   (newer-wins upsert)
  -> new tenders appear the next morning; status changes (e.g. a tender
     gets awarded) update the same row.
  To switch it on: push to GitHub + add the DATABASE_URL secret.
  Running more often adds little: PLACSP refreshes about once a day.

7. CHECKLIST EXAMPLE – TENDER 20602902
----------------------------------------------------------------------
  Cemetery-management SaaS, La Vall d'Uixó council. Budget 3,704.18 EUR
  excl. VAT. Bid deadline 20 Oct 2026 23:59. PCAP 93 pages + PPT 24 pages.
  47 items, 47/47 citations verified.
  - One envelope (sobre único) with 9 documents; 9 more only for the winner.
  - No solvency proof needed; ROLECE registration required; ENS security
    certification required (ISO 27001 does NOT replace it).
  - Criteria: price 70, availability 5, P1 response 5, P1 workaround 5,
    P1 resolution 5, extra training 10.
  - Price formula: Pi = 70 x (Bi / Bmax). Abnormally low: art. 85 RGLCAP.
  - 4 contradictions between the documents, e.g. ENS MEDIUM (PCAP p.74)
    vs BASIC (PPT p.8); minimum training 12 h (PCAP p.21) vs 4 h (PPT p.11);
    availability 99% (PPT) vs scoring from 99.5% (PCAP); extension
    23 vs 24 months.
